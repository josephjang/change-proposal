## Summary

메모를 즉시 지우는 대신 기존 메모에 삭제 시각을 기록한다. 일반 조회는 활성 메모만 반환하고, 휴지통은 아직 복원 가능한 항목만 반환한다. 복원과 만료 데이터 정리는 같은 메모의 상태를 잠금 아래에서 확인해 경쟁을 처리한다. 복원 가능 여부는 정리 작업의 실행 여부와 관계없이 판정한다.

## Non-Goals

- 별도 휴지통 저장소, 검색 엔진, 메시지 큐를 도입하지 않는다. 이 예시는 단일 데이터베이스 조회와 기존 정기 작업 실행기를 전제로 한다.
- 메모 본문 구조, 인증 방식, 백업 보관 정책을 변경하지 않는다.
- 완전한 작업 이력이나 모든 요청의 영구 중복 제거 기록을 만들지 않는다. R6은 현재 상태에서의 반복 요청을 다루며, 서로 다른 삭제·복원 작업을 하나로 합치지 않는다.
- 만료 시각에 모든 물리적 사본이 즉시 사라진다고 보장하지 않는다. 제품 경계는 [Non-Goals](2026-09-12-note-trash.requirements.ko.md#non-goals)와 [R4](2026-09-12-note-trash.requirements.ko.md#requirements)를 따른다.

## Context

문서 형식의 확인 기준은 이 저장소의 [Split form 가이드](../docs/split-proposals.md)와 두 [제품](../templates/product-requirements.md)·[기술](../templates/technical-design.md) 템플릿이다. 확인한 문서 리비전은 `c02b5fa0ed03dea431862bec690abb091ed5898f`다. 이 커밋은 문서 저장소의 기준일 뿐, 가상 앱의 코드를 검증한 리비전이 아니다.

샘플을 위한 현재 시스템 가정은 다음과 같다. 실제 적용 시에는 해당 앱의 코드 경로·심볼·테스트와 조사한 커밋으로 대체해야 한다.

- 서버가 로그인 사용자와 메모 소유자를 확인한다. 메모는 고정 ID, 소유자, 제목, 본문, 작성·수정 시각을 가진다. 공유·첨부파일·폴더·오프라인 쓰기는 없다.
- 웹 화면과 API는 함께 배포할 수 있고, 점검 중 새 요청을 막을 수 있다. 목록·검색·상세 조회는 같은 관계형 데이터베이스를 읽으며 별도 검색 인덱스나 서버 캐시는 없다.
- 데이터베이스는 트랜잭션과 행 잠금을 지원한다. 현재 삭제는 메모 행을 실제로 제거한다. 기존 정기 작업 실행기로 만료 항목을 정리할 수 있다.

이 가정 외에 해결되지 않은 제품·기술 선택은 샘플에 남겨 두지 않았다. 따라서 내용 없는 Open Questions 섹션은 생략했다.

## Design

### 상태와 저장 — R2, R3, R4, R6

기존 메모에 nullable `deleted_at`을 추가한다. 값이 없으면 활성 상태다. 삭제 시각이 있으면 휴지통 상태이며 `restore_until = deleted_at + 30×24시간`으로 마감을 계산한다. 별도 상태 열이나 마감 열은 만들지 않아 서로 다른 값으로 어긋나는 경우를 줄인다. ID·소유자·제목·본문·작성 시각은 삭제와 복원에서 바꾸지 않는다. 일반 편집이 아닌 삭제·복원은 본문의 수정 시각도 바꾸지 않는다.

```text
활성 ── 삭제 ──> 휴지통 ── 마감 전 복원 ──> 활성
                   │
                   └── 마감 도달 ──> 접근·복원 불가 ── 정리 작업 ──> 행 제거
```

마감 도달은 읽기·복원 조건의 변화이지 정리 작업이 기록하는 별도 상태가 아니다. 시각은 서버 측 데이터베이스의 UTC 시각을 기준으로 비교하고, 화면에만 현지 시각으로 변환한다. 목록의 기간 계산과 복원 판정에 같은 30×24시간 규칙을 사용한다.

### 조회·편집 경계 — R1, R2, R4, R5

일반 목록·검색·상세 조회·저장에는 소유자 일치와 `deleted_at IS NULL` 조건을 공통으로 적용한다. 휴지통 목록은 소유자가 일치하고 삭제 시각이 있으며 조회 시각이 마감 전인 메모만 삭제 시각 역순으로 반환한다. 목록에는 제목·삭제 시각·복원 마감과 복원 대상 ID만 싣고 본문은 보내지 않는다.

기존 상세 주소와 저장 요청은 휴지통 메모를 찾지 못한 것으로 처리한다. 존재하지 않거나 다른 소유자의 메모도 동일한 일반 오류로 응답한다. 제목·본문·삭제 여부를 권한 없는 사용자에게 오류 내용으로 노출하지 않는다. 삭제 전에 이미 화면에 전달된 본문을 다른 탭에서 소급해서 지우는 것은 보장하지 않지만, 이후 저장이나 재조회는 이 조건을 반드시 거친다.

### 상태 전환과 요청 결과 — R1, R3, R4, R5, R6

삭제·복원·편집은 대상 메모의 행 잠금을 얻은 뒤 현재 상태를 다시 읽는다. 사용자 작업은 잠금을 얻은 뒤에도 소유자를 확인한다. 마감 판정 시각은 요청을 받은 시각이나 트랜잭션 시작 시각이 아니라 **잠금을 얻은 뒤 읽은 데이터베이스 시각**이다.

| 요청 | 처리 | 사용자에게 전달할 결과 |
|---|---|---|
| 활성 메모 삭제 | 잠금 아래에서 `deleted_at`을 현재 시각으로 설정하고 커밋 | 성공 후 목록·검색·편집 화면을 갱신 |
| 복원 가능한 휴지통 메모에 삭제 재요청 | 기존 삭제 시각을 유지 | 이미 삭제된 상태를 성공으로 반환 |
| 마감 전 복원 | `deleted_at`만 비우고 커밋 | 기존 ID를 반환하고 원래 메모로 이동 |
| 이미 활성인 메모에 복원 재요청 | 내용·ID를 바꾸지 않음 | 같은 메모를 반환 |
| 만료·존재하지 않음·타인 소유 메모에 복원 요청 | 변경하지 않음 | 동일한 “복원할 수 없는 메모” 오류와 새로고침 안내 |
| 휴지통 메모 편집 | 변경하지 않음 | 저장 실패를 알리고 목록으로 돌아갈 수 있게 함 |

만료된 메모는 삭제 재요청에서도 접근 불가로 처리한다. 복원과 삭제처럼 **서로 다른 작업**이 겹치면 잠금을 획득해 처리한 순서가 결과를 결정한다. 복원 후 새 삭제는 새 기간을 시작하지만, 휴지통 상태에서 반복된 삭제는 기간을 늘리지 않는다.

응답 전 커밋을 완료한다. 데이터베이스 오류는 트랜잭션을 취소한다. 응답이 유실되면 클라이언트는 성공으로 단정하거나 삭제를 자동 재전송하지 않고 일반 목록·휴지통을 다시 조회한다. 사용자가 상태를 확인한 뒤 다시 시도할 수 있다. 한 탭의 작업 성공 후에는 그 탭의 관련 조회 결과를 갱신하며, 다른 탭은 다음 조회·저장 시 서버 상태를 확인한다.

### 만료 데이터 정리와 운영 — R4, R5

기존 정기 작업 실행기로 매시간 소량씩 만료 후보를 찾는다. 각 메모의 잠금을 얻은 뒤에도 삭제 시각과 마감을 재검사하고, 여전히 만료된 행만 제거한다. 후보 조회 뒤 먼저 복원된 메모는 건너뛴다. 작업이 중단되면 다음 실행에서 남은 후보를 처리하며 별도 완료 표식은 필요 없다.

정리 실패는 복원 기한을 늘리지 않는다. 모든 읽기·복원 경로가 자체적으로 마감을 확인하기 때문이다. 제거 건수·실패 건수·마지막 성공 시각을 기록하고 기존 작업 실패 알림에 연결한다. 사용자 요청 로그는 작업 종류와 성공·실패 이유를 남기되 메모 제목·본문은 기록하지 않는다. 운영 로그와 정리 작업은 사용자에게 접근 권한을 부여하는 별도 경로가 아니다.

## Technical Decisions

- **TD1: 기존 행에 삭제 시각을 두고 복원한다.** 별도 휴지통 테이블로 행을 옮기는 대안은 원래 ID와 내용의 보존, 두 저장 위치 간 전환을 추가로 다뤄야 한다. 이 구조에서는 같은 행을 유지하는 편이 [PD3](2026-09-12-note-trash.requirements.ko.md#product-decisions)와 R3에 직접 대응한다. 대신 모든 일반 조회·편집에 필터를 적용해야 하는 위험을 수용한다. 별도 검색 저장소를 도입할 때 재검토한다.
- **TD2: 만료 판정과 물리적 정리를 분리한다.** 정리 작업이 행을 지웠는지로 복원 가능 여부를 정하면 작업 지연이 R4의 제품 정책을 바꾼다. 요청 시 마감을 비교하고 정리는 나중에 수행한다. 모든 사본의 삭제 시한이 요구되면 제품 정책과 함께 재설계한다.
- **TD3: 상태 전환을 행 잠금으로 직렬화한다.** 조회 후 조건 없는 저장은 오래된 편집 내용이 휴지통 상태를 덮거나, 정리 작업이 방금 복원한 메모를 삭제할 수 있다. 단일 데이터베이스라는 가정 아래 잠금 후 상태 재검사를 선택한다. 분산 이벤트 처리나 별도 검색 엔진까지 확장하는 설계는 현재 범위에 필요하지 않다.

## Test Strategy

아래는 구현 시 수행할 **계획과 기대 관찰**이다. 실행 결과가 아니다. 메모 ID와 제목·본문을 고정한 데이터, 서로 다른 두 사용자, 조절 가능한 서버 시각을 사용한다.

| 요구사항 | 검사 방법 | 기대 관찰 |
|---|---|---|
| R1 | 삭제 후 목록·검색·직접 주소 재조회. 커밋 실패와 커밋 후 응답 유실을 각각 주입 | 성공한 삭제만 일반 조회에서 제외. 오류 시 성공으로 오인하지 않고, 결과 불명확 시 재조회로 실제 상태 확인 |
| R2 | 두 사용자의 휴지통 조회, 서로 다른 시간대에서 표시 확인 | 자기 메모의 제목과 시각만 보임. 표시 시간대가 달라도 같은 마감 순간을 가리킴 |
| R3, PD3 | 삭제 전후 ID·제목·본문·작성 시각을 비교하고 복원 후 원래 주소와 검색 확인 | 원래 메모가 그대로 돌아오고 휴지통에서는 사라짐 |
| R4, PD1 | 마감 직전·정확히 마감·직후에 복원. 정리 작업을 멈춘 채 만료 조회. 요청을 마감 전에 시작하고 잠금은 마감 후에 획득 | 직전 처리만 복원 가능. 만료 행이 남아 있어도 조회·복원 불가. 오래된 휴지통 화면은 실패 안내 후 갱신 |
| R5, PD2 | 다른 사용자의 ID로 각 조회·삭제·복원·저장 시도. 삭제 전 탭에서 저장. 휴지통 응답과 로그 검사 | 권한 없는 내용·존재 여부 미노출. 삭제 후 저장 거부. 휴지통 본문과 로그의 제목·본문 미포함 |
| R6 | 삭제·복원 반복, 두 연결에서 삭제와 복원 경쟁, 복원 후 새 삭제 | 휴지통에서 재삭제해도 기한 불변. 복원 재요청은 같은 ID. 서로 다른 작업은 처리 순서대로 반영되고 새 삭제만 기한 갱신 |
| R3, R4 및 TD3 | 복원이 마감 직전에 잠금을 얻고 마감 후 커밋하는 동안 정리 작업을 시작. 이미 복원된 행이 남은 후보 목록에 들어 있는 경우도 재검사. 별도로 저장과 삭제 경쟁 | 먼저 허용된 복원은 완료되고 정리는 활성 행을 건너뜀. 저장이 먼저면 저장된 내용이 휴지통에 남고 삭제가 먼저면 저장 거부 |

전환 검사는 기존 메모가 모두 활성으로 남는지, 새 버전의 모든 읽기 경로가 삭제 필터를 적용하는지, 만료 정리 중단이 복원 기간을 바꾸지 않는지를 포함한다. 실제 화면의 안내 문구·시간대·통신 오류 경험은 브라우저에서 수동으로도 확인한다. 단위 테스트만으로 동시 요청의 순서나 화면 경험을 검증했다고 보지 않는다.

## Verification

- Checked: 없음. 가상의 앱이므로 구현 코드, 테스트 명령, 실행 리비전, 통과 결과가 없다.
- Not checked: 위 Test Strategy 전체, 데이터 전환, 동시성, 실제 브라우저 동작. 이 샘플의 문서 검토가 기능 검증을 대신하지 않는다.
- 실제 변경 기록으로 사용할 때는 각 검사에 대해 테스트한 커밋 또는 실행 식별자, 관찰 결과, 생략한 검사와 이유를 기록한다. 계획을 복사해서 통과 결과처럼 쓰지 않는다.

## Risks & Migration

- 기존 데이터에는 `deleted_at = NULL`을 적용해 모두 활성 메모로 유지한다. 이미 실제 삭제된 메모를 복원할 데이터는 없으며, 이는 제품 Non-Goals와 같다. 소유자별 휴지통 조회와 만료 후보 탐색에 필요한 인덱스도 이때 추가한다.
- 출시 시 짧은 점검 시간을 잡고 요청 유입과 진행 중 쓰기를 멈춘다. 스키마를 확장한 뒤 웹과 API를 모두 삭제 상태를 이해하는 버전으로 전환한다. 모든 일반 읽기·편집 경로와 복원 흐름을 확인한 다음 서비스를 열고 정리 작업을 켠다. 기존 버전과 새 버전이 함께 쓰는 전환은 이 샘플의 범위 밖이다.
- 삭제된 행을 무시하지 못하는 구버전으로 되돌리면 메모가 다시 노출될 수 있다. 단순한 코드 롤백이나 새 열 삭제는 하지 않는다. 문제가 생기면 정리 작업을 우선 멈추고, 삭제 필터와 보관된 데이터를 유지한 채 수정 배포한다. 물리적으로 제거된 행은 이 기능으로 되돌릴 수 없다.
- 가장 큰 구현 위험은 목록·검색·상세·편집 중 한 경로에서 필터를 빠뜨리는 것이다. R1/R5 통합 검사를 배포 전 확인 항목으로 둔다. 별도 검색 인덱스·캐시·공유 기능이 실제 제품에 있다면 Context의 가정이 깨지므로 그대로 적용하지 않는다.
- 정리 작업 장애로 만료 데이터가 더 오래 저장될 수 있다. 기존 운영 알림으로 탐지하되, 사용자에게 약속한 열람·복원 기한과 물리적 저장 기간을 혼동하지 않는다. 제품에서 받아들인 보관·마감·점검 시간의 영향은 [Risks](2026-09-12-note-trash.requirements.ko.md#risks)에 모아 둔다.
