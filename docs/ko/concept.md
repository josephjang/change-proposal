# 개념: 변경 제안 (Change Proposal)

> `docs/concept.md`의 한국어판. 어긋나면 영어판을 따른다.

## 정의

**변경 제안(Change Proposal, CP)**은 제품이나 시스템에 대한 하나의 변경 뒤에 있는 판단을 기록한 한 장짜리 마크다운 파일이다: 왜 하는지, 무엇을 일부러 하지 않는지, 무엇을 결정하고 무엇을 버렸는지, 실제로 무엇을 검증했는지, 무엇을 알고 감수하거나 미뤘는지. 사람이 쓰고, 저장소 안에 살며, 변경과 같은 PR로 머지된다.

세 가지 성질이 이를 정의한다.

- **묘사가 아니라 판단을 기록한다.** 코드, 스키마, 인터페이스는 스스로를 설명한다. 제안은 코드가 복원할 수 없는 것을 담는다.
- **변경과 함께 다닌다.** 같은 저장소, 같은 PR, 같은 리뷰, 같은 이력. 머지 후에는 그 변경의 기록이다.
- **작다.** 한 장. 다섯 섹션. 그보다 커지게 하는 것은 묘사이거나(코드에 속한다) 패턴이다(카탈로그에 속한다).

## 왜 "제안"인가

이 문서의 첫 번째 일이 작업과 함께 의도를 리뷰어 앞에 두는 것이고, 명세와 달리 해법을 기술하려 하지 않기 때문이다. 문서는 제안한다: 문제는 이것이고, 이것은 하지 않을 것이며, 이렇게 결정하고 이것을 포기했다. 머지 뒤에도 여전히 제안이라 부르며, main 브랜치에 있다는 사실이 실행되었음을 말한다.

## 코어

**트리거.** 관찰 가능한 동작을 바꾸는 변경은 제안을 갖는다. 바꾸지 않는 변경 — 동작이 같은 리팩터, 오타, 의존성 패치, 테스트만 — 은 갖지 않는다; PR 설명에 그렇다고, 그리고 어떻게 확인했는지 적는다.

**위치.** `docs/changes/YYYY-MM-DD-<slug>.md`, 코드와 같은 PR에 커밋.

**형태.** 제목과 고정 레이블의 다섯 섹션:

| 섹션 | 담는 것 |
|---|---|
| **문제 (Problem)** | 지금 무엇이 누구에게 왜 불편한가, 근거는 무엇인가. 필요하다면 지금 어떻게 동작하고 왜 그렇게 만들어졌는가. "무엇을 만든다"가 아니다. |
| **비목표 (Non-goals)** | 이 변경이 일부러 하지 않는 것과 그 이유. 최소 하나. 변경이 커지는 것을 막는 선. |
| **결정 (Decisions)** | 대안이 있었던 결정만. 각각: 무엇을 골랐고, 무엇을 버렸고, 사실이 바뀌면 결론도 바뀌는 종류의 이유. 없으면 지운다. |
| **검증 (Verification)** | 실제로 무엇을 확인했고 무엇을 관찰했나. 무엇을 확인하지 않았고 왜인가. |
| **감수한 리스크와 미룬 것 (Risks & deferred)** | 알고 받아들인 트레이드오프. 발견했지만 일부러 하지 않은 개선과 이유. |

**저작.** 사람이 쓴다. AI가 돕는지, 어떻게 돕는지는 코어가 정하지 않는다.

**크기.** 한 장. 쓸 게 없는 섹션은 채우지 않고 지운다.

**그 외에는 없다.** front matter도, 상태 필드도, 티어도, 리뷰 단계도, 마커도, 설정도 없다.

## 코어가 일부러 정하지 않는 것

코어는 실천법으로서 완결되어 있다: 팀은 몇 년이든 코어만으로 쓸 수 있다. 동시에 팀이 나중에 필요로 할 수 있는 모든 것에 대해 의도적으로 침묵한다. 각 침묵은 패턴이 채운다 — 그 패턴이 이름 붙인 상황을 팀이 실제로 만났을 때만.

| 코어가 말하지 않는 것 | 그것을 정하는 패턴 |
|---|---|
| 변경이 얼마나 커야 한 장 이상, 리뷰어 한 명 이상이 필요한가 | `risk-signals`, `sizing-tiers` |
| 머지된 제안은 어떻게 되는가 — 고쳐도 되는가, 어떻게 뒤집는가 | `supersession` |
| 제안의 메타데이터는 무엇인가 — 담당자, 상태, 링크, 태그 | `proposal-metadata` |
| 검증 섹션 외에 "끝났다"는 무엇인가 | `success-criteria` |
| diff를 열지 않을 독자에게 무엇이 바뀌었는지 어떻게 설명하는가 | `before-after` |
| 코드를 쓰기 전에 제안을 리뷰하는가 | `design-first-review` |
| 프로토타입과 실험은 어떻게 하는가 | `spike-then-spec` |
| AI가 작성에 어떻게 참여하는가 | `human-ai-split` |
| 검증에서 무엇이 증거로 인정되는가 | `evidence-verification` |
| 현재-상태 문서를 어떻게 정직하게 유지하는가 | `living-docs-bridge` |
| 변경보다 오래 사는 결정은 어디로 가는가 | `decision-promotion` |
| 제안 하나보다 큰 일은 어떻게 조직하는가 | `initiative-umbrella` |
| 결과를 나중에 누가 보는가 | `outcome-review` |
| 코딩 에이전트는 제안을 어떻게 쓰는가 | `agent-context`, `agent-skills` |
| 도구가 무언가를 강제하는가 | `lint-gate` |
| 제안을 어떤 언어로 쓰는가 | `multilingual-records` |

패턴을 도입하지 않은 팀은 그것이 "빠진" 것이 아니다. 신호를 아직 만나지 않은 것이다.

## 무엇이 아닌가

| 이것이 아니다 | 이유 |
|---|---|
| 제품 요구사항 문서(PRD) | PRD는 제품 영역을 기술한다. 제안은 하나의 변경을, 그것도 코드가 말할 수 없는 것만 기술한다. |
| 설계 문서 / RFC | 설계 문서는 해법을 기술한다. 제안은 그 안의 결정을 기술하고 나머지는 코드를 가리킨다. |
| 아키텍처 결정 기록(ADR) | ADR은 하나의 변경보다 오래 사는 결정을 담는다. 제안은 한 변경 안의 결정을 담는다. (`decision-promotion`이 둘을 잇는다.) |
| PR 설명 | PR 설명은 리뷰어에게 diff를 설명하고 잊힌다. 제안은 나중에 찾아 읽도록 쓴다. 동작 변화가 없는 변경에서는 PR 설명이 기록의 전부다. |
| 체인지로그 | 체인지로그는 사용자에게 무엇이 바뀌었는지를, 제안은 왜·무엇을 버렸나·무엇을 감수했나를 말한다. |
| 티켓 | 티켓은 작업을 추적하고, 제안은 이유를 담는다. 서로 링크한다. |
| 위키 페이지 | 위키는 현재 상태를 기술하고 제자리에서 고친다. 제안은 하나의 전이를 기술한다. |
| 세션 기록 | AI와의 대화 기록은 원재료다. 제안은 사람이 거기서 추린 것이다. |

## 크기: diff가 아니라 영향 반경

코어의 크기 질문은 정확히 하나 — *동작이 바뀌는가?* — 이고, 변경이 무엇을 하는지를 보고 답한다. 몇 줄을 건드렸는지, 얼마나 걸렸는지, 사람이 썼는지 AI가 썼는지는 보지 않는다. 동작이 같은 2,000줄 기계적 리팩터에는 제안이 필요 없다. 권한 체크 한 줄 변경에는 필요하다. 더 세밀한 판정은 `risk-signals`와 `sizing-tiers` 패턴이다.

## 배경

이 실천법은 코드, 요약, 검증 로그가 싸게 만들어지는 — AI의 도움으로 만드는 — 팀을 위해 다듬어졌다. 코어가 작은 이유(초안이 공짜라서 길이가 실패 양상이 된다), 묘사보다 판단을 고집하는 이유(묘사는 AI가 가장 잘하고 가장 먼저 낡는다), 검증이 "무엇을 했나"가 아니라 "무엇을 *관찰했나*"를 묻는 이유가 그것이다. 그러나 코어 자체는 AI에 대해 아무것도 전제하지 않는다. AI가 어떻게 참여하는지는 `human-ai-split`, 에이전트가 제안을 어떻게 읽는지는 `agent-context`다.

## 어휘

| 용어 | 뜻 |
|---|---|
| **변경(Change)** | PR로 전달되는, 제품이나 시스템에 대한 하나의 의도된 수정. |
| **제안(Proposal)** | 위에서 정의한 문서. 약자 CP. 머지 후에는 그 변경의 기록이기도 하다. |
| **섹션(Section)** | 다섯 코어 부분 중 하나, 또는 패턴이 더한 부분. |
| **레이블(Label)** | 섹션의 고정 영문 이름(`Problem`, `Decisions`, …). 패턴은 하나의 공유 표(`docs/patterns/README.md`)에서 레이블을 더한다. |
| **판단(Judgment)** | 사람만 줄 수 있는 내용: 프레이밍, 경계, 결정과 이유, 무엇을 감수하나. 다섯 코어 섹션은 판단이다; 검증은 증거에 대한 판단이다. |
| **패턴(Pattern)** | 신호가 명시된, 독립적으로 도입할 수 있는 코어에의 선택적 추가. `docs/patterns/`. |
| **신호(Signal)** | 패턴을 도입할 때가 되었음을 알려 주는 관찰 가능한 상황. |
| **조합(Composition)** | 저장소가 도입한 패턴의 집합. `docs/changes/README.md`에 적는다. |
